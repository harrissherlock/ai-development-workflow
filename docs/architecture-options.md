# AI 开发协作系统：交互式开发与后台 Agent 自主开发

## 1. 目标与方案概览

围绕 ChatGPT、GitHub、GitHub Actions 和 Vercel，建立可以复用的软件开发流程。以 FocusOS 为示例，支持需求讨论、代码修改、自动测试、在线预览和正式发布。

两种方案共享代码仓库、测试流程和部署平台，区别主要在于代码开发的执行者、运行环境和任务调度方式。

| 项目 | 方案 A：ChatGPT Work 直接开发 | 方案 B：后台 Agent 自主开发 |
| --- | --- | --- |
| 用户入口 | ChatGPT 对话 | ChatGPT 对话或 GitHub Issue |
| 开发执行者 | 当前 Work 任务中的编程助手 | OpenHands 等独立运行的开发 Agent |
| 工作方式 | 开发期间持续交流和调整需求 | 提交明确任务后，由后台系统执行 |
| 执行环境 | 平台提供的工作空间 | 自托管服务器或托管 Agent 服务 |
| 任务进度 | 对话中的进度信息及 GitHub PR | GitHub Issue、PR 和 Agent 任务记录 |
| 自动测试 | 当前环境及 GitHub Actions | Agent 环境及 GitHub Actions |
| 页面预览 | Vercel Preview | Vercel Preview |
| 关闭对话后 | 按平台具体任务能力执行 | 独立服务可以继续执行 |
| 环境维护 | 主要由平台负责 | 自托管时由用户负责 |
| 适合任务 | 需求探索、界面调整、频繁反馈 | 要求明确、耗时较长、重复性开发 |

本文的任务编号、网址和执行记录均为使用流程示例。具体产品权限、运行限制和集成方式，应在实施时检查。本文描述系统设计，不表示相关集成已经配置完成。

## 2. 共享系统与职责

| 组件 | 职责 |
| --- | --- |
| ChatGPT | 讨论需求、编写开发任务、参与开发和审查结果 |
| GitHub | 保存代码，以 Issues、分支和 Pull Requests 管理开发工作 |
| GitHub Actions | 自动执行代码检查、类型检查、测试和构建 |
| Vercel | 构建 Web 项目，提供预览部署和正式部署 |
| 后台 Agent | 在方案 B 中读取任务、修改代码、运行测试并提交 PR |
| 任务调度服务 | 在方案 B 中接收事件、分配任务、保存执行状态并控制重试 |

GitHub Actions 可以充当两种方案共同的标准检查环境。Vercel 通过 Git 集成部署项目；预览部署和 CI 可以同时运行。正式发布采用人工确认合并 PR、合并后自动部署的流程，并配置必需的状态检查。

### CI 与 CD

- **CI（Continuous Integration，持续集成）**：提交代码后自动进行检查、测试和构建。
- **持续交付（Continuous Delivery）**：通过自动检查后，软件具备发布条件，正式发布保留人工决定。
- **持续部署（Continuous Deployment）**：满足发布条件后自动部署软件。

测试通过说明已配置的检查通过。检查范围应覆盖项目的重要行为，例如任务日期保存、页面交互和数据同步。

## 3. 方案 A：ChatGPT Work 直接开发

### 3.1 工作环境

ChatGPT 在当前可用的工作空间中获取仓库代码、安装依赖、修改文件并运行检查。提交代码和创建 PR 需要相应的 GitHub 写入权限；实际可执行操作由当前工具、网络和平台能力决定。

GitHub 保存开发成果，GitHub Actions 执行自动检查，Vercel 提供在线预览。需要 Windows 本地接口的功能，可以交由对应的 Windows 环境验证。

### 3.2 用户体验与开发样例：FocusOS 日历功能

#### 第一步：在 ChatGPT 中提出需求

用户可以输入：

> 帮我给 FocusOS 增加日历视图，参考 Notion Calendar 的设计风格。支持月视图、周视图、拖动任务修改日期，并与现有任务系统同步。请修改开发分支，完成测试后创建 PR，并给我 Vercel 预览网址。

#### 第二步：ChatGPT 执行开发

典型操作如下：

1. 读取项目结构、现有任务数据和开发说明。
2. 明确日历视图与任务系统的数据关系。
3. 创建开发分支，实现月视图、周视图和拖动功能。
4. 检查任务日期保存、刷新后数据恢复及移动端显示。
5. 运行项目已有的检查和相关测试，修复发现的问题。
6. 提交代码，创建或更新 PR。
7. 查询 GitHub Actions 和 Vercel 的执行结果。
8. 在可访问预览环境时操作页面，验证主要流程。

用户可以在对话中看到简要进度，例如：

> 已完成月视图和任务日期同步，正在检查周视图拖动及日期保存。

完成后，交付信息可以包含：

- PR：#42，新增日历视图。
- 自动检查：通过。
- 预览网址：由 Vercel 实际生成并返回。
- 检查内容：视图切换、拖动修改日期、刷新后保留修改、移动端显示。

#### 第三步：打开预览并调整需求

用户打开预览网站后，可以在同一对话中继续输入：

> 任务卡片改成紧凑风格，周视图增加时间轴，拖动时显示目标日期。

ChatGPT 根据反馈继续修改当前分支，运行相关检查并更新 PR。Vercel 为新提交生成更新后的预览部署。

#### 第四步：确认并发布

用户检查功能和页面后确认合并。满足仓库检查要求后，将 PR 合并到正式分支，Vercel 自动部署正式版本。

**实际体验：提出需求 → 开发过程中交流 → 打开预览 → 提出修改意见 → 确认合并。**

### 3.3 优点与使用条件

- 可以边讨论边开发，适合需求尚在变化的功能。
- 页面设计和交互细节可以通过连续反馈逐步完善。
- 无需单独维护后台 Agent 服务器。
- 执行时间、工具权限、网络访问和后台任务能力受当前平台环境影响。

## 4. 方案 B：后台 OpenHands Agent 自主开发

### 4.1 后台 Agent 是什么

后台 Agent 是独立运行的开发程序。它调用模型理解需求，在执行环境中修改代码、运行命令和测试，并将成果提交到 GitHub。

系统通常包含：

1. **模型服务**：提供代码生成和错误分析能力。
2. **Agent 执行程序**：例如 OpenHands，负责操作文件和开发工具。
3. **运行环境**：提供 CPU、内存、磁盘及隔离的任务工作目录。
4. **任务调度服务**：连接 GitHub 事件和 Agent，管理任务状态、重试及交接。

从 GitHub Issue 自动领取任务、在 CI 失败后继续修复、接收 PR 修改意见及发送完成通知，都需要选定版本支持的集成能力或额外配置。

### 4.2 部署位置

| 部署方式 | 适合情况 | 需要管理的内容 |
| --- | --- | --- |
| 托管 Agent 服务 | 希望快速开始并减少服务器维护 | 服务权限、套餐、模型和项目配置 |
| 云服务器自托管 | 希望独立持续运行，便于接收 GitHub 事件 | 服务器、容器、更新、备份和凭据 |
| PVE 中的 Linux 虚拟机 | 希望利用现有硬件，连接本地开发资源 | 虚拟机、Docker、网络和任务服务 |

结合现有 PVE 环境，可先考虑独立 Linux 虚拟机运行 Docker 和 Agent。调用远程模型 API 时通常不需要本地 GPU。资源需求应根据项目依赖、浏览器测试和并发数量评估。

Vercel 在这套设计中负责部署 Web 项目。后台 Agent 使用独立的开发执行环境。

### 4.3 用户体验与开发样例：FocusOS 日历功能

#### 第一步：在 ChatGPT 中提交后台开发任务

用户可以输入：

> 给 FocusOS 增加日历功能，支持月视图、周视图和拖动任务修改日期。交给后台 Agent 开发，完成后创建 PR、运行测试并提供预览网址。

ChatGPT 将需求整理为 GitHub Issue。示例任务如下：

**Issue #56：新增日历视图**

- 支持月视图和周视图切换。
- 显示现有任务，并允许打开任务编辑界面。
- 拖动任务后更新日期，与现有任务存储同步。
- 刷新页面后保留日期修改。
- 提供移动端可用的交互方式。
- 为日期更新和数据保存补充必要测试。
- 提交 PR，附上检查结果和 Vercel 预览地址。

Issue 添加已配置的任务标签，例如 `agent-task`，调度服务接收任务。

#### 第二步：后台独立执行

任务调度服务和 Agent 按以下过程工作：

1. 领取任务，记录任务执行者和状态。
2. 创建独立工作目录及开发分支。
3. 获取代码，安装项目依赖。
4. 实现功能并运行相关测试。
5. 分析错误，修改代码并重新检查。
6. 提交代码，创建 PR。
7. 等待 CI 和预览部署结果。
8. 在已配置的反馈机制下继续处理失败结果。
9. 完成后更新任务状态，提供 PR、预览网址及测试摘要。

独立运行服务正常工作时，用户可以关闭 ChatGPT 页面和 Windows 电脑。Agent 所在服务器需要保持运行。

#### 第三步：回来查看结果

用户通过 GitHub 或 Agent 的任务界面查看结果。配置通知渠道后，也可以接收完成通知。

示例结果：

> Issue #56 已完成，成果提交至 PR #57。相关自动检查通过，Vercel 预览已生成。请通过 PR 中的地址查看月视图、周视图和任务拖动效果。

#### 第四步：提交修改意见

用户发现周视图拖动体验需要调整，可以输入：

> 周视图拖动时增加目标时间提示，任务卡片改为紧凑显示，请继续处理原任务。

ChatGPT 将修改要求更新到原任务。已配置的调度服务触发 Agent 继续处理，Agent 更新同一 PR 并重新运行检查。

#### 第五步：确认并发布

用户查看最新预览，确认后合并 PR。Vercel 自动更新正式网站。

**实际体验：提交明确任务 → 后台执行 → 离开电脑 → 查看 PR 和预览 → 提交反馈或确认合并。**

### 4.4 后台模式的主要优点

- **独立持续执行**：任务进度由后台服务管理，减少反复发送继续开发指令。
- **响应开发事件**：可以配置 Issue 标签、CI 结果或 PR 修改意见触发任务。
- **自动修复循环**：可以读取 CI 日志、修改代码并重新提交。
- **运行环境可配置**：可以安装项目需要的依赖、数据库及浏览器工具。
- **模型选择更灵活**：在兼容范围内选择模型服务，并设置成本限制。
- **支持多个独立任务**：配置并发调度和隔离环境后，可以分别处理不同分支。

相应地，需要维护运行服务、任务状态、访问凭据和费用限制。复杂需求仍可能需要用户作出产品或技术决定。

## 5. CI 自动检查与自动修复样例

假设 Agent 已提交日历功能，GitHub Actions 返回：

```text
ESLint: Passed
TypeScript: Passed
Unit Tests: Passed
Playwright: Failed

Dragging a task to another date does not update its saved due date.
```

这表示浏览器测试发现拖动后的任务日期没有正确保存。

方案 A 中，ChatGPT 在当前任务内读取结果、修改代码并重新检查。方案 B 中，调度服务可以接收失败事件，将日志交给负责该 PR 的 Agent 继续处理。

建议为后台修复设置以下控制：

- 只处理授权仓库及 Agent 负责的 PR。
- 根据事件标识去除重复通知。
- 检查结果对应的提交，忽略已被新提交替代的失败事件。
- 设置最大修复次数、运行时间和模型费用。
- 修复代码后重新运行相关检查，保持测试要求。
- 达到限制后保存当前成果、失败日志和待处理问题，等待人工决定。

## 6. 两种方案如何协作

两种模式可以共用 GitHub Issues、分支、PR、GitHub Actions 和 Vercel。

| 场景 | 处理方式 |
| --- | --- |
| 同一任务由 ChatGPT 开发 | 后台 Agent 暂不修改该任务分支 |
| 同一任务由后台 Agent 开发 | ChatGPT 查看进度、讨论需求并记录反馈 |
| 更换任务执行者 | 当前执行者保存代码，释放任务；新执行者读取最新提交和任务状态 |
| 同时处理不同任务 | 分别使用独立分支和工作目录 |
| 不同任务涉及同一文件 | 通过 PR 审查和合并冲突处理协调修改 |
| CI 失败 | 由当前负责该任务的执行者处理 |

后台任务领取应采用可避免重复领取的状态更新机制，并设置超时恢复。Issue 标签用于展示状态，实际执行权由调度服务管理。

## 7. Skill、插件与任务调度的分工

| 形式 | 在系统中的作用 |
| --- | --- |
| Skill | 保存需求分析、项目检查、代码开发、测试和交付流程 |
| GitHub、Vercel 插件或工具 | 提供仓库、PR、部署和日志等操作能力 |
| GitHub Actions | 根据事件执行固定的自动检查任务 |
| 后台任务调度服务 | 接收任务、启动 Agent、保存状态并处理重试 |
| 自定义 MCP Server | 在现有工具不足时，提供额外的统一操作接口 |

Skill 可以复用开发规范。后台持续运行还需要独立执行程序和任务调度。初期优先复用现有 GitHub、Vercel 和 Agent 集成，按实际缺少的能力增加自定义工具。

## 8. 推荐实施顺序

1. **完成共享基础配置**：确认项目可以构建，连接 Vercel，建立 PR 预览。
2. **建立自动检查**：在 GitHub Actions 中运行项目相关的代码检查、测试和构建。
3. **完成方案 A 的一次完整开发**：从需求到 PR、预览、修改反馈和合并。
4. **整理可复用开发流程**：将项目命令、开发要求和交付要求写入仓库说明或 Skill。
5. **部署单个后台 Agent**：先通过明确任务验证代码修改、测试及 PR 创建。
6. **接入任务调度**：增加任务领取、状态保存、CI 反馈、重试限制和完成通知。
7. **按需求扩展并发**：在单任务流程稳定后增加多个隔离执行环境。

对于 FocusOS，可优先使用方案 A 完善界面与交互，把要求明确的功能、维护和修复任务逐步交给方案 B。两种方式共享同一套自动检查与预览发布流程。
